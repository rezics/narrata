## 结果

实现 [ADR 0022](../../../../docs/adr/0022-authoring-publication-and-reader-map.md) §1、§2 与 §7 实现表的第一行：
新 crate `packages/narrata/tooling/crates/narrata-authoring` 的内存创作 API，供以后的 authoring
Wasm 与 CLI 共用。

1. **草稿记录 v1**（§1）：六种 kind 的受检类型与严格 JSON（拒绝重复键与未知字段，现有
   `canonical_json` 规范化），`assembleRecords` 与 `splitSource` 互逆：拆分、组装、规范化后的
   源稿相同，编译得到相同构件与 lock；`deriveDraftIndexes`（每选项一行，`control`/`unresolved`
   标记）；1 MiB 记录上限与 `record_too_large`。生成 `draft-record.schema.json`。
2. **多错校验**（§2）：`validateRecord` 与 `validateProject` 收集全部诊断，`complete: false`
   与 `limit` 诊断表示达到预算；诊断报告 v1 的形状照 §3 末段。从 `compile.rs` 抽出共用的语义
   检查，旧的 `compile` 入口与它的错误行为保持不变，两条路径共用同一套规则。
3. **内存铸造**（§2）：`mintIds(edit, occupied)` 复用 `narrata-node-tools` 的 `Minter` 算法，时钟与
   随机源由调用方注入（测试中确定），不读写文件。把 `Minter` 的算法移到 `narrata-authoring`，
   CLI 改为调用它。
4. **内存 compose**（§2）：`composeSource(source, previous?, mode)` 是现有 `compose` 的内存核心，
   `previous` 为受检的上次程序（`Program::from_pack` 打开的 pack 即可，对象集合输入留给发布
   任务）；返回应追加的墓碑记录与新 lock，`locked` 模式与首次发布 `compared: false` 照 ADR。
   CLI 的 `compose` 改为文件适配器调用它，现有 CLI 行为与 `products/gamebook-demo` 的输出逐字节
   不变。
5. **冻结语料** `fixtures/compat/draft-records-v1/`：示例作品"山口来信"的规范记录集合与组装后
   的 R2 源稿，附生成说明；测试两次生成逐字节相同并能组装、编译出现有构件。

## 约束

- 只做上面五项；发布对象集合、关系投影、读者地图、Wasm 与 npm 接口是后续任务，不要提前搭建。
- 不改 R2 源稿、lock v2、程序 CBOR、pack 与任何现有冻结语料；不加 ADR 之外的格式或选项。
- 并行任务在同一 crate 中改 `runtime.rs` 与 `narrata-nodes/Cargo.toml`（共享执行轨迹），不要碰
  它们；新模块在 `lib.rs` 中声明。
- `narrata-authoring` 必须能编译到 `wasm32-unknown-unknown`（铸造的时钟与随机源由调用方提供）。
