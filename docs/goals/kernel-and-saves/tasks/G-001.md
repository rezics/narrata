## 结果

一个按历史深度参数化的存档基准，测出**现有** `SaveStore` 实现随提交数增长的代价，作为之后
窄存储契约与按行 SQLite（见 [存储与存档](../../../contracts/storage-and-saves.md)）的对照基线。
Goal 的验收是"1K 与 10K 次提交时单次提交与加载延迟同一量级"；本任务只建立测量并记录现状，
不修任何性能问题。

测量（`MemoryStore` 与 `SqliteStore` 各一组，同一套代码，按深度 N 参数化）：

1. 深度 N 的会话上再提交一次的延迟（经 `SessionCoordinator` 派发一个输入）。
2. 打开深度 N 的存档到可继续状态的延迟（`load_save` 或等价的打开路径）。
3. 导出深度 N 的 `CheckpointBundle` 的延迟与字节数。

N 取 100、1K、10K。现有实现每次提交都对全部对象做 `validate_all`（`memory.rs:227`），SQLite 每次
操作整库加载并整库重写（`narrata-store-sqlite/src/lib.rs:192,409,762`），构建 10K 深度的历史
可能要数小时：先用小 N 测出增长曲线，构建时间超过约 10 分钟的组合不跑，在结果里写明"未测，
外推约 X"并给出依据。构建历史的代价不计入被测时间。

基准必须在存储改造之后仍能编译运行：只经 `SessionCoordinator`、存档与 bundle 的公开 API 驱动，
不依赖 `MemoryStore`/`SqliteStore` 的内部字段；后端由一个构造函数参数化，以后换成新后端只改这一处。
用 `narrata-testkit` 的生成器（如 `branch_call_choice_v0` 或能无限推进的程序）产生长历史；
如果没有能推进到 10K 步的现成程序，在 bench 文件内构造一个最小的循环程序，不要改 testkit。

## 交付

- `crates/narrata-store/benches/` 与（如需要）`crates/narrata-store-sqlite/benches/` 中的 criterion
  基准，命名按能力（如 `history.rs`），在 `scripts/benchmark-g2.ps1` 中运行。可以把 SQLite 的组放在
  `narrata-store` 中、以 dev-dependency 引入 `narrata-store-sqlite`（cargo 允许 dev 依赖环），或给
  `narrata-store-sqlite` 加 criterion，二选一，取改动小的。
- `docs/development/benchmarks/storage.md`：本机（见 [章程资源](../../manager.md#资源)）测得的表格，
  每格是中位数；写明命令、日期、提交和未测组合的外推。只写数字和怎么复现，不写分析散文。
- 允许为基准新增依赖造成的 `Cargo.lock` 改动，列入 OWNER CHANGES。

## 不要做

不改 `src/` 下任何代码，不做优化，不加计数包装器（后续的契约任务提供），不改 testkit 和冻结语料。
