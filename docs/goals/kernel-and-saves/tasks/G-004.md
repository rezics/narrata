## 结果

`narrata-store` 的领域逻辑——引用与类型化引用（目录头、归档、复合存档）的 CAS、输入幂等、pin、
Effect 账本（claim、lease、outcome、fence、补偿）、GC、完整性扫描、bundle 导入导出——在
[ADR 0012](../../../adr/0012-narrow-storage-backend-contract.md) 的 `StorageBackend` 之上**只实现
一次**，内存与 SQLite 只是两个后端。Goal 的验收由本任务交付：

- 1K 与 10K 次提交时，单次提交与加载（打开到可继续状态）的延迟同一量级，内存与 SQLite 都是；
  用 `crates/narrata-store/benches/history.rs`（G-001 的基线，结果在
  `docs/development/benchmarks/storage.md`）重测并把新数字写在基线旁边。
- 加载单个提交不触发全对象枚举、读取的对象数不随历史深度增长：用 `narrata_storage::testing`
  的计数包装器断言（深度 10 与深度 1000 的读取计数相同，且 `scan_objects` 为零）。
- 现有 `tests/model.rs`、`tests/faults_gc.rs` 以及其余 store 测试对任意后端运行（至少内存与
  SQLite 两个后端各跑一遍）；故障注入改用 `FaultInjecting`，原子性断言改用分页扫描比较前后状态，
  包括"执行后报错"（结果未知）的情形。
- `fixtures/compat/stage5-v0` 的全部摘要与字节不变；`task check:g5` 通过。

## 读什么

ADR 0012 全文，尤其"`SaveStore` 如何映射到原语"一表与 touch 键的 GC 宽限期设计——那是本任务的
设计输入，你可以在发现问题时修改它，并在引擎 ADR 里说明。`narrata-storage` 的
`testing/conformance.rs` 与 `tests/wrappers.rs` 是测试写法的样板。基线测量与现状：
`memory.rs:227`（每次提交 `validate_all` 全部对象）、`coordinator.rs:1814-1890`（每次加载沿父链
走到创世提交，约 2N 次读）、`coordinator.rs:942`（`redo_candidates` 全对象扫描）、
`narrata-store-sqlite/src/lib.rs`（整库加载与重写，`edge_rows` 逐个解码 Program）。

## 已定的方向

- **一个引擎，多个后端。** 默认做法：保留 `SaveStore` 作为引擎的接口（这样 `SessionCoordinator`、
  协议引擎、CLI 的调用点基本不动），由一个 `impl<B: StorageBackend>` 实现一次；`MemoryStore`、
  `SqliteStore` 成为引擎加对应后端的类型别名或薄包装。`list_*` 一次返回全部的方法删除或改为
  分页；调用它们的地方（bundle 导出、debugger、CLI `timeline log`、协议引擎）改用分页扫描或
  索引键。若保留 `SaveStore` 反而别扭，可以换成引擎结构体，理由写进 ADR。
- **领域对象图集中在一处。** GC 标记、bundle 闭包、完整性扫描需要"某个对象引用了哪些对象"：
  按种类解码出边的逻辑只写一次（一个函数或 trait），不要散落在 GC、bundle、校验各处。以后把通用
  部分搬进 `packages/narrata/kernel`、让 Flow/Statechart/节点注册各自的种类时，这里就是接缝。
  本任务不做这次搬移，也不做通用的领域注册。
- **加载只读需要的对象。** 提交时校验新对象及其直接引用（父提交存在且链接正确、快照与程序
  匹配），由归纳保证闭包完整；加载只校验目标提交、它的快照和程序，不再沿父链走到创世提交。
  需要祖先的操作（回退、导出、`ensure_ancestor`）在访问时校验所访问的部分。导入 bundle 照旧
  完整重新校验。若需要"已验证水位"之类的记录，它只能由引擎自己的校验写入（见调研报告"主要
  风险"）。在 ADR 里写明信任边界：后端不被信任，读取时重新校验摘要；丢失的祖先在访问时报错。
- **索引键代替扫描。** 子提交索引（`redo_candidates`、debugger 计数）、程序索引、边索引、目录
  操作幂等键等按 ADR 0012 的映射表落成键空间。
- **修订号。** 引用修订号改用后端的全库修订号。先核实修订号确实不进入任何对象字节或导出格式
  （冻结语料测试会告诉你）；断言"修订号为 1、2……"的测试改为断言相对关系。
- **SQLite。** `narrata-store-sqlite` 改为"引擎 + `narrata-storage-sqlite`"，删除整库加载与重写。
  旧 schema v2 库需要迁移路径：**在改写之前**，用现有代码生成一个小的 v2 库（含提交链、引用、
  目录、账本条目、pin）冻结到 `fixtures/compat/store-sqlite-v2/`（带 SHA-256 清单与预期内容），
  再实现"打开 v2 库时迁移到新格式"（或显式的迁移函数 + CLI 入口，二选一，写进 ADR），测试读这份
  冻结库并在迁移后继续会话。
- **新格式的冻结语料。** 键布局确定后，用新引擎生成一份 SQLite 库与它的键/对象清单冻结到
  `fixtures/compat/store-layout-v1/`，测试保证以后的版本能打开它。

## 不要做

- 不改 Program、Snapshot、Receipt、Commit、bundle、manifest 的任何字节或摘要；不改
  `fixtures/compat/stage5-v0`。
- 不做"浅存档"（bundle 只带目标提交而不带全部祖先）：它改变 bundle 语义，需要单独的 ADR；
  导出的字节数随深度增长在本任务内保持现状，在交接里给出数字。
- 不改协议引擎的存储注入方式（它仍用内存后端；只做让它继续编译与通过测试的最小改动，如
  `list_*` 的替换）。宿主批次协议、IndexedDB 是下一个任务。
- 不改 `narrata-core`（除非为编译所必需的最小改动，列入 OWNER CHANGES）；不改节点栈。
- 不做 async、PostgreSQL 或其他后端。
