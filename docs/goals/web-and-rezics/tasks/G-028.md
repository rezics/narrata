## 结果

GitHub Actions `ubuntu-latest` 上 `cargo test --workspace` 偶发失败（运行 37327218627，前一次同一
提交通过）：

```text
test concurrent_openers_of_a_new_file_share_one_schema ... FAILED
called `Result::unwrap()` on an `Err` value: Busy
```

四个线程同时 `SqliteBackend::open` 同一个新文件时，有一个在约 60 ms 内得到 `Busy`，远短于
5 秒的 `busy_timeout`。`open_with` 先设 `busy_timeout`，再执行 `PRAGMA journal_mode = WAL`，
初始化在 `BEGIN IMMEDIATE` 中进行（`src/lib.rs`）。SQLite 在某些锁状态下切换日志模式会直接返回
`SQLITE_BUSY` 而不调用 busy handler，这是首要怀疑，但先查清。

修复打开路径，让并发打开者在 `busy_timeout` 之内等待或有界重试，而不是立即报 `Busy`；超过
`busy_timeout` 仍报 `Busy`。ADR 0012 对打开的承诺（空库初始化、标识与版本检查、并发打开同一新
文件不冲突）不变。用一个压力测试复现并证明修复：多轮、多线程同时打开新文件，以及打开与写入
交错；测试在本机稳定、耗时有界。本机复现不了 Linux 的时序时，在交接中说明依据。
