# Narrata 的目标

更新：2026-10-29。本页说明 Narrata 要成为什么，比任何单个 Goal 都长寿；具体取舍见
[编号决定](decisions.md)，当前工作见 [GOAL.md](../../GOAL.md)。

## 结果

**Narrata 是通用叙事引擎，目标是让复杂叙事变得容易。**

作者用它描述节点、选择、状态与后果；引擎负责确定性执行、存档、时间旅行、迁移和分析；
正文、选项文字、图像、声音等真实内容由内容方提供。同一部作品可以在网站、本地游戏和
生成式（AI）体验中运行，内容可以持续增加，而已有存档和时间线不被破坏。

## 首要场景

当前交付顺序是正文与分支选择型 Gamingbook，然后是纯 Web 传统视觉小说与按需资源分发，见[决定 18](decisions.md#18-先交付-gamebook再推进-web-vn)。本地游戏和生成式叙事仍保留为后续场景。

| 场景 | 宿主 | Narrata 交付什么 | 存档在哪里 |
| --- | --- | --- | --- |
| 网站互动小说 | REZICS（首个宿主）或其他 Web 产品 | Wasm 运行时与 TypeScript 包、阅读器外壳（正文通过渲染插槽交还宿主）、图视图、供宿主数据库查询的关系投影 | 浏览器 IndexedDB；登录用户经存储契约增量同步到宿主服务器（[决定 15](decisions.md#15-服务器存档实现同一个存储契约)） |
| Web 传统视觉小说 | REZICS 或其他 Web 产品 | 逐句对白、可恢复场景与媒体状态、按需剧情和资源加载；见[待启动 Goal](../goals/web-vn/GOAL.md) | 复用浏览器与宿主服务器存档基础 |
| 本地游戏 | Unity、Godot、Bevy、自研引擎 | 原生库与 C/C#/Rust 绑定、内容包加载、存档字节 | 宿主自己的存档系统（Steam Cloud、主机平台存档 API 等） |
| 生成式叙事 | AI 游戏、动态内容服务 | 结构与状态权威、动态节点与选项、呈现键 | 同上；生成结果由内容方按呈现键缓存 |

REZICS 是第一个落地宿主，但 Narrata 不只服务 REZICS：所有接口都与内容方无关，REZICS
只是其中一个内容方和宿主。

## 原则

1. **结构归引擎，内容归内容方。** Narrata 保存节点、选择、状态、历史和对内容的引用，
   不保存正文。内容的本地化、审核、授权和生命周期由内容方负责。
2. **确定性优先。** 相同的构件、状态和输入得到相同的结果；任何会影响走向的外部结果都作为
   输入记录下来，回放与时间旅行不依赖重新调用外部服务。
3. **存档跨版本存活。** 稳定身份、墓碑、显式迁移和重放分歧检测让作品在发布后继续演化。
4. **规模来自分块与身份，不来自数据库。** 运行时只读不可变构件，按需加载，峰值内存与
   活跃部分成正比。
5. **复杂度由引擎和第一方能力承担。** 作者使用默认套件即可写 Gamebook、互动小说和对话；
   需要时再替换能力或策略。

## 规模目标

- 单部作品 10 万个选择点。以局部选择为主时约为数千个内容单元（见
  [选择粒度调研](../research/2026-10-05-choice-granularity-and-scale/choice_granularity.md)）。
- 读者端峰值内存与当前活跃的程序块数成正比，而不是与作品总量成正比。
- 本地游戏中每次选择的引擎处理时间以毫秒以下为目标；网页首屏只下载清单与首个程序块。

这些数字是设计目标，由合成作品基准验证并在基准结果出来后修订。宿主可以有更小的当前
规模：REZICS 按其现有量级接入，不为 30 万章节做准备。

## 非目标

- 不做正文编辑器、内容管理、本地化平台或媒体制作管线；它们是其他产品。
- 不在运行时查询任何数据库，也不把图数据库当作运行时存储。
- 不承诺通用的 exactly-once 外部副作用；宿主提供幂等键、事务接口或显式未知结果处理
  （见 [Effect 与宿主状态](../architecture/effects-and-host-state.md)）。

## 路线

1. 内核去文本、内容引用与选择模型，以及 kernel、窄存储契约与可移植存档的既有基础继续复用。
2. [Gamebook SDK](../../packages/narrata/web/README.md)：首发交付创作/发布、阅读、按需加载与在线存档的固定包，供宿主接入；完整阶段补齐图、演化与维护，并验证、交接和收敛。实际交付版本与验收范围见[固定输入](../integrations/rezics.md#narrata-自己的交付依赖)。一个平台运行时和阶段内兼容继续按决定 17。
3. REZICS 按[能力请求](../integrations/rezics.md)实施自己的存储、权限与界面；准备好后用固定包做真实联合验收。Narrata 不修改 REZICS，模拟宿主验收不等同产品上线。
4. [Web VN Goal](../goals/web-vn/GOAL.md)：在 Gamebook 交付基线上增加传统 VN 语义、可恢复播放器与媒体按需分发；当前待启动，先完成范围移交和格式 ADR。
5. 之后按具体作品需要推进本地游戏、人物关系、同伴、任务和作者工作台；[重建提案](../../archive/2026-09-05-rebuild-proposal.md)保留长期方向，不作为首发功能清单。

## 以后

维护者 2026-10-05 讨论确定的方向，第一阶段不实施，开始实施时先写 ADR。

**声明式能力（类似 Nix）。** 程序包分为清单、逻辑构件、分析构件和可选的运行时模块。清单声明
程序需要的能力（节点类型、领域、Effect 能力、宿主接口版本），发布时解析出确切的提供者并锁定
（类似 `flake.lock`）；存档记录创建它的程序构件与锁。标准程序只声明能力、不打包运行时，由
平台提供；高度定制的程序可以自带模块。运行时按"kernel 版本 + 一组能力模块"静态构建并按输入
求摘要，常见组合预构建缓存，所有版本像构件一样保留。浏览器中同时运行多个版本没有服务端成本；
平台不再要求一个运行时永久兼容所有历史格式，迁移按每个运行时声明的前驱逐步执行（ADR 0020 的
多跳路径）。打包与否主要影响存储和流量，不影响经济模型。

真正要处理的是信任与修补：平台运行时可以在声明的约束内重新解析到修补版本，自带运行时只能被
拒绝加载；自带运行时是作者的代码，只能是 Wasm，在隔离环境（如 Web Worker）中只经宿主接口
与外界交互，不能在宿主域名上执行脚本。届时宿主接口宜做成消息协议，标准运行时也走同一条路。

待定的产品问题：

- 定制的边界：只改逻辑（节点类型、Effect、领域，界面与正文仍由 Narrata 与宿主渲染），还是也
  允许自带整个界面（独立域名的沙箱 iframe，正文以数据交给它）。
- 自带模块的来源：平台从源码可复现地构建，还是作者上传编译好的 Wasm。
