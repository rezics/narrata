# Industry Narrative Engines, Authoring Tools & Interchange Formats: Data Models, Logic/Content Separation, Storage, Scale and Updates

Scope note: These notes compare script-language engines (ink, Yarn Spinner, Twine/Twee + story formats, ChoiceScript, Inform/Glulx, Ren'Py, Naninovel, Dialogic), data-first authoring tools (articy:draft, Arcweave, Pixel Crushers Dialogue System), proprietary studio pipelines (Valve Response System, Larian Osiris, Bethesda Creation Kit, CD Projekt RED quest editor, Supergiant/Hades, Failbetter StoryNexus), and specs (Twine 2 HTML, Twee 3, Treaty of Babel, Quetzal, W3C SCXML, Narrative Context Protocol). Research date: 2026-10-04. Where a claim comes from a search-engine excerpt, a secondary source, or community reverse-engineering rather than a primary document, it is marked **[secondary]** or **[community]**.

---

## Q1. How do engines and tools separate narrative logic from text and media? Where does text live, and how is media referenced?

### Takeaway
There are three patterns. (a) **Text inline with logic, compiled together**: ink, Twine, ChoiceScript, Ren'Py, Inform. (b) **Logic compiled to bytecode that refers to lines by stable ID, with text in per-language string tables**: Yarn Spinner, Bethesda lstrings, Naninovel localization docs, Dink-for-ink. (c) **A database or object model with text as fields on records**: articy, Arcweave, Dialogue System for Unity, Valve rules, Osiris DBs. In almost every system, media goes in as an **opaque ID, tag or command that the host interprets**: ink tags and external functions, Yarn commands and line-ID asset lookup, Dialogue System `Sequence`, Arcweave asset IDs, Valve "response" = vox file. That is strong precedent for treating text and media as separate products keyed by ID.

#### Supporting detail
- ink describes itself as "a scripting language for writing interactive narrative, both for text-centric games as well as more graphical games," and states "ink isn't designed as an end-to-end narrative game engine. Rather, it's designed to be flexible, so that it can slot into your own game and UI with ease." — [inkle/ink README](https://github.com/inkle/ink)
- ink tags carry media cues inline with the text, e.g. `Passepartout: Really, Monsieur. # surly # really_monsieur.ogg`. Tags can be dynamic (`#{character}_greeting.jpg`). The host reads `currentTags` after each `Continue()`, `TagsForContentAtPath("knot")` for knot tags, and `globalTags`. — [RunningYourInk.md](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)
- ink external functions (`EXTERNAL playSound(soundName)` + `BindExternalFunction`) let script trigger host actions. They are treated as side-effecting "Actions" by default. "Pure" functions should be marked `lookaheadSafe = true` because the runtime evaluates ahead speculatively. ink-side fallback functions run when the binding is absent. — [RunningYourInk.md](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)
- Yarn Spinner: "the Yarn Spinner compiler separates your Yarn script into two pieces: the code, and the _string table_." String tables "are always associated with a language", and the original script language is the "base language". — [Yarn Spinner v1 docs](https://v1.yarnspinner.dev/docs/unity/components/yarn-programs/)
- Yarn line IDs appear as `#line:1a64a5` at the end of a line and can be auto-generated. A Line Provider "receives line IDs from the Dialogue Runner, and fetches the localised line and localised line assets". Voice-over is "intimately tied to localisation". — [Yarn Spinner docs: Assets & Localization](https://docs.yarnspinner.dev/yarn-spinner-for-unity/assets-and-localization)
- Heaven's Vault: ink scripts worked as an "interactive film script", with each line either a scene direction ("show camera shot", "play sound") or dialogue. Joseph Humfrey said ink handled "all the narrative stuff and all the presentation stuff and all the sequencing stuff", while the engine applied cinematography automatically. This let conversations written for one location be reused in five or six locations. — [Game Developer](https://www.gamedeveloper.com/design/knockin-on-i-heaven-s-vault-i-how-inkle-designed-its-first-3d-game)
- Valve: "You have a database of rules, each with a list of criteria about the state of the world that must be met for the rule to be considered a match. A rule has an associated 'response' which is simply the thing that happens when a rule matches, such as a voice file or an animation." — [Ruskin, GDC 2012 slides (Valve)](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Arcweave conditions store arcscript as strings (`"script": "not have_potion"`), and code blocks inside element HTML use `<pre><code class="language-arcscript">`. The host engine must interpret both. — [Arcweave JSON docs](https://docs.arcweave.com/integrations/json)
- Dialogue System for Unity: "At runtime, the Dialogue System treats your dialogue database as read-only and loads the database values into Lua where the current values can be checked and changed during play." **[secondary: search excerpt of Pixel Crushers docs]** — [Pixel Crushers Logic & Lua](https://www.pixelcrushers.com/dialogue_system/manual2x/html/logic_and_lua.html)
- Emily Short's storylet definition has three parts: content ("a line or a whole section of dialogue... narration... an animation or scrap of film"), prerequisites, and effects on world state. This is a content-agnostic model, the same shape as Valve rules and Yarn node groups. — [Emily Short, "Storylets: You Want Them"](https://emshort.blog/2019/11/29/storylets-you-want-them/)

### Inferences
- ink is the main outlier: text is embedded in the compiled logic artifact. Production users then build sidecar ID/string pipelines (see Q6). Yarn Spinner, Bethesda, articy X and Dialogue System all key text by stable IDs. For Narrata, this supports making line IDs first-class in the core IR and keeping strings out of it.
- Valve, Arcweave, ink tags and Dialogue System `Sequence` all treat media as an opaque reference the host resolves. This is direct precedent for "text/media are separate products": the core only needs to emit typed references or events.
- Heaven's Vault shows the risk of splitting too far. inkle found value in letting writers put presentation cues (camera, sound) in the same script. A pure-logic core still needs a well-defined, extensible channel for authored presentation directives, not just text IDs.

### Gaps
- Primary docs for Fungus (Unity), Chat Mapper, and Unreal's dialogue plugins were not retrieved, so their data models are not covered.
- Harlowe and Chapbook internal state models were not retrieved; only SugarCube's (Q3) was.
- Obsidian's Pillars/Pathfinder tooling and Ubisoft narrative tooling: no public primary documentation found.

## Q2. What are the storage, serialization and interchange formats, and how are they versioned?

### Takeaway
Shipping runtimes almost all consume a **compiled, read-only, versioned artifact**: ink JSON, Yarn protobuf `.yarnc`, Glulx/Z-code story files, Twine HTML, articy JSON/XML, Arcweave JSON. Authoring sources are text (ink, Yarn, Twee, `.nani`, `.dtl`, Osiris goals) or proprietary project databases (articy, Arcweave, CK plugins). Versioning is usually a single integer format version with a minimum-compatible floor (ink). Silent schema changes in tool exports break custom integrations (Arcweave 5.11).

### Cited Findings
- **ink runtime JSON**: the top level has `inkVersion` (format version integer) and `root` (outermost Container). Containers are arrays whose final element is special (`null` or an object with named sub-containers, `#f` bit flags for visit/turn counting, `#n` name). Text is `"^..."`. There are about 20 control commands (`"ev"`, `"/ev"`, `"out"`, `"pop"`...). Variables are `{"VAR=": ...}` / `{"VAR?": ...}`. Paths are dot-separated with indices and `^` parent references. — [ink_JSON_runtime_format.md](https://github.com/inkle/ink/blob/master/Documentation/ink_JSON_runtime_format.md)
- The ink format doc's example still shows `"inkVersion": 10` ([doc](https://github.com/inkle/ink/blob/master/Documentation/ink_JSON_runtime_format.md)). The current runtime source has `inkVersionCurrent = 21` and `inkVersionMinimumCompatible = 18`, and rejects files outside that range ([Story.cs](https://github.com/inkle/ink/blob/master/ink-engine-runtime/Story.cs)). The doc also does not describe tags or list definitions. In other words, the public format spec lags the implementation.
- ink release history: 0.9.0 replaced extensive state copying with a "patching system so that only small 'diff patches' get created during evaluation". 1.0.0 added multiple parallel flows. The latest release shown is 1.2.1 (dated "May 5"; year not captured in the fetch), adding a universal-binary inklecate for macOS. The runtime also offers `CopyStateForBackgroundThreadSave()` / `BackgroundSaveComplete()`. — [inkle/ink releases](https://github.com/inkle/ink/releases)
- **Yarn Spinner compiled format**: `.yarnc` files are protobufs defined by `yarn_spinner.proto`. `Program` holds `name`, `nodes`, `initial_values` (used "when PUSH_VARIABLE instruction is run, and the value is not found in storage") and `language_version`. `Node` holds `name`, `instructions`, `headers`. Instructions include `RunLine` (by line ID), `RunCommand`, `AddOption`, `ShowOptions`, `JumpIfFalse`, `CallFunction`, `RunNode`/`PeekAndRunNode`, and (v3) `AddSaliencyCandidate` / `SelectSaliencyCandidate`. — [yarn_spinner.proto](https://github.com/YarnSpinnerTool/YarnSpinner/blob/main/YarnSpinner/yarn_spinner.proto)
- The `ysc` CLI emits a `.yarnc` program, a `-Lines.csv` string table and a `-Metadata.csv` line-metadata table **[secondary: search summary of YarnSpinner-Console]**. — [YarnSpinner-Console](https://github.com/YarnSpinnerTool/YarnSpinner-Console)
- Third-party Yarn VMs exist in C++ ([YarnMachine](https://github.com/VirtuosoChris/YarnMachine)), Go ([DrJosh9000/yarn](https://github.com/DrJosh9000/yarn)) and TypeScript ([YarnSpinner-TypeScript](https://github.com/YarnSpinnerTool/YarnSpinner-TypeScript/)). A compact, documented bytecode schema enables multiple runtimes. Likewise ink has a C++ runtime with a JSON-to-binary compiler ([inkcpp](https://github.com/JBenda/inkcpp)).
- **Twine 2 HTML output spec**: the root is `<tw-storydata>` with required `name` and `ifid` (8–63 chars per Treaty of Babel) and optional `format`, `format-version`, `startnode`, `creator`, `creator-version`, `tags`, `zoom`. Each `<tw-passagedata>` has `pid`, `name`, optional `tags`, `position`, `size`, and "passage content is stored within the `<tw-passagedata>` element itself as a single text node... all &, <, >, ", and ' characters should be escaped". — [twine-2-htmloutput-spec.md](https://github.com/iftechfoundation/twine-specs/blob/master/twine-2-htmloutput-spec.md)
- **Twee 3**: "a text format for marking up the source code of Twine stories" for interchange across compilers. Files are UTF-8 `.tw`/`.twee`. Headers look like `:: Name [tags] {"position":"600,400","size":"100,200"}`. Special passages are `StoryTitle` and `StoryData` (JSON: required `ifid`, plus `format`, `format-version`, `start`, `tag-colors`, `zoom`). Duplicate passage names should "at least... emit a warning". — [twee-3-specification.md](https://github.com/iftechfoundation/twine-specs/blob/master/twee-3-specification.md)
- **Treaty of Babel** (April 2006): each published IF work gets an IFID of 8–63 chars (digits, capitals, hyphens), generated by the design system with no central authority, "analogous to the ISBN". It defines iFiction XML for bibliographic metadata interchange. — [Treaty of Babel](https://babel.ifarchive.org/babel_rev9.html); [IF Tech Foundation copy](https://github.com/iftechfoundation/ifarchive-if-specs/blob/main/Babel-Treaty.md)
- **Inform 7**: the Standard Rules define a physical world model (rooms, things, directions as kinds, plus relations such as containment). Games compile to Glulx (or Z-machine), and Blorb archives bundle images and sounds **[secondary]**. — [Standard Rules](https://zedlopez.github.io/standard_rules/); [Inform 7 Handbook](https://cs.wellesley.edu/~games349/InformHandbook.pdf); [ganelson/inform](https://github.com/ganelson/inform)
- **articy:draft**: "If you like to get articy:draft data into your own (game-) project and you are not using Unity or Unreal, using the JSON or XML export is a good start." XML exports all objects with an XSD. JSON is "rule-set based", filtering by type (template) or hierarchy. — [articy Technical Exports](https://www.articy.com/en/articydraft/integration/techexports/)
- articy:draft X 4.0 (Nov 28, 2023) moved to "segmented JSON files included in a single file archive or folder", exports all languages, adds a "Generic Engine" export, and gives Unity/Unreal importers incremental export with "smarter detection of changed content". — [articy Help: Changes 4.0](https://www.articy.com/help/adx/Changes_4_0.html)
- **Arcweave JSON** top-level keys: `name`, `startingElement`, `cover`, `boards`, `elements`, `connections`, `branches`, `components`, `attributes`, `assets`, `variables`, `conditions`, `locales`, `contents`. A web API JSON endpoint accepts `boardIds[]` to limit output. — [Arcweave JSON](https://docs.arcweave.com/integrations/json); [Arcweave web API](https://arcweave.com/docs/1.0/api)
- Arcweave 5.11.0 (Sept 2, 2026) "introduces component variables and unifies board and component-scoped values under the attributes data model". Custom loaders must read both `variables` and `attributes`. The guide recommends "accepting the old board-variable shape as well as the new attribute-backed shape" and warns that "plain empty strings may be represented as `null`". Official plugins required major version bumps (Unity 3.0.0, Godot 3.0.0, Unreal 2.0.0) and save re-testing. — [Arcweave migration guide](https://blog.arcweave.com/scoped-variables-in-arcweave-migration-guide)
- **Dialogic 2** timelines are plain-text `.dtl` resources with shortcode-like events and quoted parameters. — [Dialogic 2 docs](https://docs.dialogic.pro/timeline-text-syntax.html). That plain text "merge[s] cleanly" for teams is from a **[secondary]** source ([DeepWiki](https://deepwiki.com/dialogic-godot/documentation/1.3-timelines-and-events)).
- **Larian Osiris**: goals are plain-text files with INIT, KB and EXIT sections. "rules are executed from top to bottom in the single story that contains all goals from all mods" (alphabetical by goal name). — [Divinity Engine Wiki: Osiris Overview](https://docs.larian.game/Osiris_Overview)
- **CD Projekt RED (Cyberpunk 2077)**: missions are "organized into separate files that contain nodes or references to other 'files' called Questphases and Scenes". Questphases are graphs that connect through handler/socket references. Scenes hold choices, animations, audio, etc. **[community: REDmodding wiki]** — [REDmodding wiki](https://wiki.redmodding.org/cyberpunk-2077-modding/modding-guides/quest/visualize-quest-files)

### Inferences
- The dominant runtime contract is "compile authoring sources into an immutable, versioned program and load it read-only". None of the surveyed shipping runtimes reads narrative logic from a live, mutable database during play. Narrata's pluggable storage backends therefore fit best as **(a) the save/state store** and **(b) an authoring/build-time content repository**, with a compiled, content-addressed program artifact in between.
- ink's stale format doc and Arcweave's breaking 5.11 export change show that an interchange format needs a normative, versioned schema (e.g. JSON Schema/protobuf) with explicit compatibility rules. Without one, third-party consumers break silently.
- Yarn's protobuf, with its several independent VMs, is the strongest evidence that a small, documented bytecode makes ports (Wasm/FFI/other languages) cheap. That aligns with Narrata's Wasm/FFI goals.

### Gaps
- No primary documentation on Osiris's compiled story format or how compiled story data is stored in BG3/DOS2 savegames.
- Witcher 3 quest-graph data format: no primary documentation retrieved (only the GDC talk title, see Q8).
- No size or performance figures were found for compiled ink JSON of 80 Days or Heaven's Vault.

## Q3. How are saves represented, and what happens to saves (and hot reload) when content changes?

### Takeaway
Saves split into two families. **Positional VM snapshots** (ink callstack plus path-keyed visit counts; Ren'Py statement plus return stack plus pickled store; Quetzal memory/stack dumps) resume precisely but are **fragile to content edits**, because positions are structural indices or auto-generated names. **Variables plus coarse anchor** (Yarn: variables plus node name; Dialogue System: Lua variables, quest states, SimStatus; SugarCube: passage name plus `$` vars per moment) are robust to edits but cannot resume mid-node. Every system that tolerates edits relies on **explicitly named anchors**. Live/hot recompilation at runtime is generally **not** a supported production workflow.

### Cited Findings
- **ink save API**: `story.state.ToJson()` / `story.state.LoadJson(json)` — [RunningYourInk.md](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)
- **ink save JSON contents** (from runtime source): `flows` (each with `callstack`, `outputStream`, `choiceThreads`, `currentChoices`), `currentFlowName`, `variablesState`, `evalStack`, `currentDivertTarget`, `visitCounts` and `turnIndices` (dictionaries keyed by **container path strings**), `turnIdx`, `storySeed`, `previousRandom`, `inkSaveVersion` (=10) and `inkFormatVersion`. Loading throws if `inkSaveVersion` < `kMinCompatibleLoadVersion` (=8). — [StoryState.cs](https://github.com/inkle/ink/blob/master/ink-engine-runtime/StoryState.cs); [Flow.cs](https://github.com/inkle/ink/blob/master/ink-engine-runtime/Flow.cs)
- ink 0.8.0 release notes promise "Big improvements in how ink can cope with saving/loading a save state when the ink story has been changed. However, it will never be possible to make this perfect, so you should always exercise caution, especially when editing content for a game that's in production." Added variables now fall back to their declared initial values. Unknown temporaries return 0/false. **[partly via search excerpt of]** [inkle/ink releases](https://github.com/inkle/ink/releases)
- Community report (inky #253): ink assigns locations to choices and gathers incrementally (`c-0`, `g-0`...), so "Adding or removing a choice or gather will put it out of sync with your old save state". Entering via a named label "seems to be safe". No inkle reply in the thread. — [inkle/inky#253](https://github.com/inkle/inky/issues/253)
- Community report (ink #508): saved state JSON keeps growing as play proceeds; the reporter describes the script as "one neverending callstack, with each divert adding an additional stackframe" and is worried about console save-size limits. — [inkle/ink#508](https://github.com/inkle/ink/issues/508)
- **Yarn Spinner**: "It is not currently possible to save or restore the specific line that the dialogue is running." To save, store `DialogueRunner.CurrentNodeName`; to restore, call `StartDialogue(savedNodeName)`. Variables persist via `SaveStateToPersistentStorage()` / `LoadStateFromPersistentStorage()`. — [Yarn Spinner 2.5 FAQ](https://docs.yarnspinner.dev/2.5/using-yarnspinner-with-unity/faq); [current FAQ](https://docs.yarnspinner.dev/faq)
- Yarn: "The intended workflow is to generate and compile Yarn Projects at editor time, not runtime." — [Yarn Spinner FAQ](https://docs.yarnspinner.dev/faq)
- Yarn `Program.initial_values` supplies defaults when a variable "is not found in storage". A save made before a new variable was introduced therefore degrades gracefully. — [yarn_spinner.proto](https://github.com/YarnSpinnerTool/YarnSpinner/blob/main/YarnSpinner/yarn_spinner.proto)
- **Ren'Py** saves internal state ("The current statement, and all statements that can be returned to", shown images and displayables, screens and their variables, music, NVL text) and Python state ("the variables in the store that have changed since the game began, and all objects reachable from those variables") via pickle. `default` variables are always saved; unchanged `define` variables are not; mutating a field of an object does not mark it for saving. — [Ren'Py docs](https://www.renpy.org/doc/html/save_load_rollback.html)
- Ren'Py: "Ren'Py only saves the current statement, and the statement it needs to return to. It doesn't remember how it got there. Importantly, statements (including variable assignments) that are added to the game won't run." Image-name→displayable mappings are not saved, so "the image may change to a new image when the game loads again". — [Ren'Py docs](https://www.renpy.org/doc/html/save_load_rollback.html)
- Ren'Py (historic reference docs): on load, rollback proceeds until "it can find a statement that has the same name as it had when it was encountered in the log. ... When the script has changed, however, the only statements that retain their names are statements that have an explicit name specified. (These statements are labels, menu statements with an explicit name, and call ... from ... statements.) The game will rollback to the start of the most recent statement that exists in both the old and new games." User classes must "always exist with the same name in later versions of the script". — [Historic Ren'Py wiki](https://www.renpy.org/wiki/renpy/doc/reference/Saving,_Loading,_and_Rollback)
- Ren'Py engine-level: "While we usually attempt to keep save compatibility between releases, this compatibility is not guaranteed." — [Ren'Py docs](https://www.renpy.org/doc/html/save_load_rollback.html). Ren'Py 7.4 changed rollback-through-load to revert changes made in `after_load` / `config.after_load_callbacks` **[secondary: search excerpt]** — [Ren'Py incompatible changes](https://www.renpy.org/doc/html/incompatible.html)
- **SugarCube (Twine)**: history is a collection of "moments". A moment is created only on passage navigation and records "the active passage and the state of all story variables" (`$`). Non-`$` variables (e.g. `setup.x`) and passage content are not saved. Loading a save replaces the state "in its entirety". — [SugarCube guide: state, sessions and saving](https://github.com/tmedwards/sugarcube-2/blob/master/docs/guides/guide-state-sessions-and-saving.md). `Config.history.maxStates` caps history (default 40 **[secondary: search excerpt]**). Saves are said to be delta-encoded and LZString-compressed **[community: save-editor site]** — [saveeditor.online](https://saveeditor.online/twine-save-editor)
- **ChoiceScript** has native `*save_checkpoint` / `*restore_checkpoint`. Before that, authors manually copied stats into backup variables **[community: CoG forum]**. — [CoG forum: Checkpoints](https://forum.choiceofgames.com/t/upcoming-choicescript-feature-checkpoints/143790)
- **Quetzal** (Z-machine/Glulx save standard): IFF `FORM IFZS` with `IFhd` (release number, serial number, checksum of the story file), `CMem`/`UMem` (dynamic memory) and `Stks` (call/eval stacks). `CMem` is the XOR of current dynamic memory against the original story file, run-length encoded. Interpreters verify the save matches the story via header bytes at `$2`, `$12`, `$1C`. — [Quetzal 1.4 spec](https://www.ifarchive.org/if-archive/infocom/interpreters/specification/savefile_14.txt)
- **Dialogue System for Unity**: the Dialogue System Saver records database variables, quest states and SimStatus (per-entry visited tracking). `PersistentDataManager` can save "only... the state of the dialogue database" as a Lua-environment string. A Save System `Version` field lets restore code check `SaveSystem.currentSavedGameData.version`, but no migration framework is described. — [Pixel Crushers Save System](https://www.pixelcrushers.com/dialogue_system/manual2x/html/save_system.html); [PersistentDataManager](https://www.pixelcrushers.com/dialogue_system/manual2x/html/class_pixel_crushers_1_1_dialogue_system_1_1_persistent_data_manager.html)
- **Bethesda/Skyrim** (community knowledge): scripted mods and persistent records are "baked into your save" from new game. Updating quest/alias-heavy mods on an existing save often requires a new game. **[community]** — [AFK Mods knowledge base](https://www.afkmods.com/index.php?%2Ftopic%2F3676-skyrim-information-baked-into-saves%2F=); [Arcadia blog: updating mods & saves](https://arcadiamgames.wordpress.com/2015/09/14/scripting-102-updating-mods-saves-games-and-asset-permanence/)
- **Osiris**: databases set in a completed goal "will remain active and available, unless they are deleted by the goal's EXIT code". Story state is a persistent fact base. — [Osiris Overview](https://docs.larian.game/Osiris_Overview)
- **Arcweave** 5.11's data-model change told plugin users to "test runtime saves". A tool-side schema change propagates into save compatibility. — [Arcweave migration guide](https://blog.arcweave.com/scoped-variables-in-arcweave-migration-guide)

### Inferences
- The fragility mechanism is the same across ink, Ren'Py and Quetzal: saves reference content by **position or auto-generated identity**, so content edits move or delete the referent. The robust pattern is **author-stable or content-addressed IDs for every resumable point**, plus graceful defaults for new variables (ink 0.8+, Yarn `initial_values`). Narrata's time-travel save store should key positions by stable node IDs, never by instruction index alone.
- Two version numbers (ink: `inkSaveVersion` with a min-compatible floor, plus `inkFormatVersion`) are a concrete precedent for separating **save-schema version** from **content/program version**. Narrata will need a third: a **content revision ID**, so a save knows which narrative build it was made against and can be migrated.
- ink's state stores `outputStream` and evaluated runtime objects (which can include text fragments) inside the save. *Inference*: such saves embed presentation/text artifacts, which complicates language switching and content patching. A logic-only save (IDs and values) avoids this.
- Ren'Py's "added statements won't run" problem is the main hazard for dynamically updated narratives. Narrata would need explicit **migration hooks** (Ren'Py has `after_load`) or a declarative state migration step when a save is loaded against a newer content revision.
- No surveyed engine documents a supported **runtime hot reload of narrative content that preserves in-flight state**. Yarn explicitly recommends editor-time compilation. That is an opportunity for Narrata, and also a warning that no prior art covers it.

### Gaps
- No primary inkle documentation on runtime hot reload/recompile preserving state. Inky's live preview recompiles and replays, but no primary source was retrieved describing the mechanism.
- No authoritative inkle reply was found explaining save-growth (#508) or recommending mitigations.
- Ren'Py's current docs no longer contain the statement-name passage. Whether the mechanism is unchanged in Ren'Py 8.x was not verified (the historic doc is the only primary source here).
- How BG3/DOS2 handle story changes (patches) against existing saves (e.g. Osiris story merging) was not found in primary sources.

## Q4. Does any tool support swapping storage backends, and at which layer?

### Takeaway
Pluggable storage exists in shipping tools, but **only at the variable/save layer**: Yarn's `VariableStorageBehaviour`, and Pixel Crushers' `DataSerializer` plus `SavedGameDataStorer`. Content is consistently compiled or exported to an immutable artifact. Content databases (articy multi-user partitions, Arcweave cloud) exist only at **authoring time**. Valve's lead engineer argued that dialogue rule data is a poor fit for a relational schema.

### Cited Findings
- Yarn variable storage is "intentionally replaceable": most of Yarn "simply asks 'what's the value of $gold?' without concerning itself with how that value is stored or managed". Custom stores subclass `VariableStorageBehaviour` and implement `SetValue` (string/float/bool), `TryGetValue<T>`, `Clear`, `Contains`, `SetAllVariables`, `GetAllVariables`. The docs show integrating with an existing game-state system using perfect hashing to shrink saves. The default `InMemoryVariableStorage` can persist to JSON. Yarn 3 adds smart variables, which the base class handles, and generated typed C# wrappers. — [Yarn Spinner 3.1 docs: Variable Storage](https://docs.yarnspinner.dev/3.1/components/variable-storage/variable-storage)
- `GetAllVariables()` returns float/string/bool dictionaries as "a point for custom saving, editors, etc." `SetAllVariables(..., clear)` overrides storage. — [Yarn API docs](https://docs.yarnspinner.dev/2.5/api/csharp/yarn.unity/yarn.unity.variablestoragebehaviour)
- Yarn FAQ advises a "single source of truth": "Variables should either live in Yarn or live in C#, and not in both." — [Yarn Spinner 2.5 FAQ](https://docs.yarnspinner.dev/2.5/using-yarnspinner-with-unity/faq)
- Pixel Crushers Save System has three tiers: Saver components → `DataSerializer` (default `JsonDataSerializer`, or Binary) → `SavedGameDataStorer` (PlayerPrefs, or encrypted Disk on standalone). "Custom implementations of DataSerializer and SavedGameDataStorer classes are supported." — [Pixel Crushers Save System](https://www.pixelcrushers.com/dialogue_system/manual2x/html/save_system.html)
- ink offers `ObserveVariable` callbacks, so hosts can mirror state into their own systems. It has no pluggable store interface: state serializes only via `ToJson`. — [RunningYourInk.md](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)
- Valve's Ruskin: "This is not a relational database. You cannot represent this as an SQL query. If it were a relational database, you would need a row for each rule and a column for every possible criterion to appear, meaning that most rules would have thousands of NULL columns... neither efficient nor convenient." He calls it "a surjective lookup function" where keys are tuples of predicates. "The rules database can be built offline" (precomputed balanced trees). — [Ruskin GDC 2012 slides](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Valve supported multiple authoring front-ends feeding one engine format. Dota's writer used Excel with "a macro to export from this to the engine's format", and the same sheet produced the actor's paper script. Others used text stanzas edited in Notepad, or a visual tool. — [Ruskin slides](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- articy:draft X MDK offers "a query language similar to SQL to query & filter objects" and create/modify/delete/export via plugins. MDK 2.4.0 adds a Ruleset API, bulk asset import and "partition update tracking". Multi-user projects use partitions with `PartitionLoaded`/`PartitionsPublished` callbacks. **[secondary: search summaries of articy pages]** — [articy MDK](https://www.articy.com/en/articydraft/integration/mdk/); [MDK 2.4.0 news](https://www.articy.com/en/recent-updates-to-the-articydraft-x-mdk-version-2-4-0-released/)
- articy X 4.0 optimized Perforce integration for "bigger projects or slower connections" by reducing data transferred on open and partition claim. — [articy Changes 4.0](https://www.articy.com/help/adx/Changes_4_0.html)
- Arcweave serves project JSON via a web API (filterable by `boardIds[]`). The authoring database is cloud-hosted, but the runtime consumes JSON. — [Arcweave JSON docs](https://docs.arcweave.com/integrations/json); [Arcweave web API](https://arcweave.com/docs/1.0/api)

### Inferences
- **Evidence for Narrata's thesis**: abstracting state storage behind an interface is proven and expected (Yarn, Pixel Crushers). Separating serializer from storer (Pixel Crushers) maps cleanly onto Narrata's "SQLite backend + JSON + Postgres" ambition.
- **Evidence against or caution**: no shipping engine found executes narrative logic against a pluggable live content DB. Ruskin's argument suggests relational schemas are a poor native representation for sparse predicate rules. A graph DB backend for *content* would be novel and needs justification (e.g. authoring collaboration, live-ops content delivery) rather than runtime querying. A defensible split: **content repository (pluggable, authoring/build/live-ops) → compiled immutable program (runtime) → state/save store (pluggable)**.
- articy's partitions and Arcweave's board-filtered API show that **partial loading/sync of content subsets** is valued at authoring scale. A backend interface should support subset or partition queries, not just whole-project load/save.

### Gaps
- No public evidence found of any engine using PostgreSQL or a graph DB as a runtime narrative content store, including live-service games. Absence of evidence in this survey is not proof of absence.
- articy's on-disk/server project storage format and multi-user server architecture are not publicly documented in the retrieved sources.

## Q5. How do tools cope with very large content (scale limits, partitioning, streaming)?

### Takeaway
Shipped narrative games reach 10^5–10^6 lines or words: 80 Days ~750k words, Disco Elysium >1M words, BG3 ~2M words (community estimate), L4D >10k lines, Hades >22k lines. The documented pain points are mostly **authoring-tool performance** (articy froze on Disco Elysium) and **save growth** (ink), not runtime CPU. The proven mitigations are **partitioning by speaker, region or level, with streaming** (Valve), **splitting content into many files or graphs** (CDPR quest → questphase → scene), and **multi-user partitions** (articy).

### Cited Findings
- Disco Elysium's script is "over a million words" per ZA/UM ([DualShockers](https://www.dualshockers.com/disco-elysium-script-length-one-million-words/)). Helen Hindpere (via Noclip, reported by PC Gamer/Yahoo, Jan 2026): "we were writing too much"; articy "got quite janky—at some point froze completely, because it definitely wasn't built for it"; articy's developers said "this is the first time anyone's coming with those problems to us". — [Yahoo/PC Gamer](https://tech.yahoo.com/gaming/articles/disco-elysium-had-much-text-032304926.html)
- 80 Days: ~750,000 words; another source cites "more than 700,000 words, 150 cities, and 16,000 individual choices" **[secondary; exact attribution between sources unclear]** — [IF50: 80 Days](https://if50.substack.com/p/2014-80-days); [Wikipedia: 80 Days](https://en.wikipedia.org/wiki/80_Days_(2014_video_game)); [Game Developer: open sourcing ink](https://www.gamedeveloper.com/design/open-sourcing-80-days-narrative-scripting-language-ink)
- Baldur's Gate 3: ~2 million words; 114,921 lines in Patch 5 vs 110,869 at launch; ~1,888 characters with dialogue **[community data-mining, not Larian-confirmed]** — [PC Gamer](https://www.pcgamer.com/baldurs-gate-3-tool-discovers-theres-around-1888-characters-with-dialogue-in-the-gamethough-justice-for-karlach-was-actually-the-main-reason-it-was-made/); [Wikipedia: BG3](https://en.wikipedia.org/wiki/Baldur%27s_Gate_3)
- Hades: "over 22,000 lines of dialogue" fully voiced by a studio of "fewer than 20" — [GDC 2021 talk article](https://gdconf.com/article/dive-into-the-dialogue-of-hades-at-gdc-2021/); [Game Developer](https://www.gamedeveloper.com/audio/dive-into-the-dialogue-of-i-hades-i-at-gdc-2021). Another write-up cites "over 300,000 words with 8500 voice lines by Zagreus" **[secondary, citing an infographic]** — [Videlais](https://videlais.com/2021/01/10/game-log-hades/)
- Valve: Left 4 Dead had "over ten thousand lines... moderate by RPG standards". Optimizations: sort criteria alphabetically for linear matching with early reject; bucket rules by hashed constant predicates (e.g. speaker, concept); "If you can get down to about fifty rules per bucket, and each rule has an average of eight criteria, you can do a lookup in less than a microsecond"; search buckets in decreasing score order. Region partitioning: "cut your rules up into individual databases by region... you don't even need to keep, say, the Italy rules in memory. Leave them on disk. Stream dialog rules in with the level data", with "global" rules always loaded. Facts can be partitioned the same way: "dump the entire table of England facts from memory when in some other region". — [Ruskin GDC 2012 slides](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Yarn Spinner: "There is no real technical limit on the number of Yarn scripts or the size of Yarn Projects." — [Yarn FAQ](https://docs.yarnspinner.dev/faq)
- ink save state grows as play proceeds (issue #508). The runtime moved to diff patches during evaluation (0.9.0) and offers background-thread save copies. — [ink#508](https://github.com/inkle/ink/issues/508); [ink releases](https://github.com/inkle/ink/releases)
- Cyberpunk 2077 splits quests into quest files referencing questphase graphs and scene files **[community]** ([REDmodding wiki](https://wiki.redmodding.org/cyberpunk-2077-modding/modding-guides/quest/visualize-quest-files)). CDPR's Sarah Gruemmer (GDC 2024) discussed "the advantages and disadvantages of complex visual scripting tools based on different engine and tool iterations" — [GDC Vault](https://www.gdcvault.com/play/1034181/)
- articy X 4.0: segmented JSON export and incremental Unity/Unreal import with change detection. These scale features target large projects and frequent re-exports. — [articy Changes 4.0](https://www.articy.com/help/adx/Changes_4_0.html)
- QBN scaling, per Emily Short: "In the mid-range, it's possible to drop in modular elements of new content alongside old content and be relatively sanguine about how you're affecting the rest of the system". But "the list of available storylets gets overwhelming for the player" at large sizes. — [Emily Short, Beyond Branching](https://emshort.blog/2016/04/12/beyond-branching-quality-based-and-salience-based-narrative-structures/)

### Inferences
- For "ultra-long" narratives, the bottleneck evidence points to **(1) authoring tool responsiveness on huge single projects, (2) save size and history growth, and (3) memory for all content resident at once**. Valve's region streaming and CDPR's file splitting suggest Narrata's composable node packages should be **independently loadable and unloadable units**, with a small always-resident "global" set.
- Narrata's time-travel save store faces ink's save-growth problem in amplified form. SugarCube bounds it with `maxStates` and deltas; ink uses diff patches. A delta-based store with compaction or snapshots is the natural mitigation (*inference*).
- Content-addressed or incremental builds (articy incremental export) matter at scale. Recompiling the whole narrative per edit would hurt iteration on million-word projects (*inference*; no ink compile-time figures found).

### Gaps
- No public numbers on ink compile times or runtime memory for 80 Days, Heaven's Vault or Overboard.
- No primary Larian source for BG3 dialogue volume or tool performance at that scale.
- No primary details on Witcher 3 quest-system scale from the GDC talk ([GDC Vault](https://gdcvault.com/play/1028897/10-Key-Quest-Design-Lessons)). Only the abstract was available.

## Q6. How is localization handled, and how does that interact with logic/text separation?

### Takeaway
ID-keyed string tables are the industry norm (Yarn, Bethesda, articy X, Naninovel, Dialogue System field suffixes, Arcweave `contents/{iso}`). ink's inline text has no built-in localization, so studios bolt on extraction pipelines (hash IDs, `#id:` tags, per-language recompiled JSON). These pipelines are brittle under source edits and force authors to drop generative text composition.

### Cited Findings
- Yarn: strings exported to CSV for translators ("Export Strings as CSV"). Built-in localization or the Unity Localization package ("easier to setup" vs "more features, but requires a lot of setup"). Voice-over requires localization setup even for one language. — [Yarn Spinner docs](https://docs.yarnspinner.dev/yarn-spinner-for-unity/assets-and-localization)
- Yarn 3 "Shadow lines" (`#shadow:departure`) reuse one localized line across nodes. — [Yarn Spinner 3.0: What To Expect](https://yarnspinner.dev/blog/yarn-spinner-30-what-to-expect/)
- ink in production (Road to Guangdong, 6+ languages): English strings extracted from compiled JSON (`^` prefix), IDs generated as `ID_CompiledInkFilename_HashOfString`, spreadsheets sent to vendors, then **per-language compiled ink JSON** generated by search-and-replace (longest strings first). The developer abandoned "any ink which was going to generatively create text from grammars". "Edits to the English source Ink scripts... are likely to break the auto-localisation." — [inkle/ink#529](https://github.com/inkle/ink/issues/529)
- Dink (Ian Thomas/wildwinter): ink "was never designed for lines of dialogue, particularly spoken dialogue". Dink adds `#id:` tags (e.g. `#id:intro_XC5r`) that double as audio filenames, emits strings files, PO/POT, Excel recording scripts and localization docs, plus a runtime JSON with speaker metadata per line. — [wildwinter/Dink](https://github.com/wildwinter/Dink); [Ink-Localiser](https://github.com/wildwinter/Ink-Localiser)
- articy X 4.0: nearly all text properties localizable and voice-over capable; localization state ("final or outdated"); DeepL; Excel localization export with word stats per speaker. — [articy Changes 4.0](https://www.articy.com/help/adx/Changes_4_0.html)
- Arcweave multi-language export puts text at `/contents/{itemId}/content/{languageIsoCode}/text`, with `_status` translation tracking and `locales` with ISO codes. — [Arcweave JSON](https://docs.arcweave.com/integrations/json)
- Bethesda: each localized plugin needs `.STRINGS`, `.ILSTRINGS` (dialogue subtitles) and `.DLSTRINGS` (books) per language, referenced by lstring IDs. Missing files crash the game/CK on language switch. **[community]** — [Beyond Skyrim wiki](https://wiki.beyondskyrim.org/wiki/Arcane_University:File_Localization); [xTranslator](https://github.com/MGuffin/xTranslator)
- Naninovel: script localization documents contain an ID line, a source-text comment and the translation. Regeneration "will respect previously generated localization documents and preserve localized entries when the source material hasn't changed". — [Naninovel localization](https://naninovel.com/guide/localization)
- Dialogue System: localized fields by suffix (e.g. `Description ru`). — [Pixel Crushers DB docs](https://pixelcrushers.com/dialogue_system/manual/html/dialogue_database.html)

### Inferences
- Stable line IDs are the shared key for localization, voice-over files, analytics and save positions. Generating them in the compiler (Yarn) rather than by hashing text (Road to Guangdong) avoids churn when text is edited. Narrata should assign author-stable IDs that survive text edits and treat text hashes only as change-detection metadata.
- Runtime text composition (ink glue, inline conditionals, grammars) conflicts with translation. If Narrata's core is logic-only, composition should happen in a separate text product with locale-aware templates (e.g. ICU/Fluent-style), not by concatenating fragments in the VM (*inference*).

### Gaps
- No primary inkle statement was found on how inkle localized Heaven's Vault or other titles.
- Larian's and CDPR's localization pipelines (BG3, Cyberpunk) are not documented in retrieved primary sources.

## Q7. Are there universal or interchange narrative formats or statechart standards, including 2023–2026 efforts?

### Takeaway
No widely adopted universal interactive-narrative interchange format exists. Successful "standards" are narrow: Twine 2 HTML and Twee 3 (one tool family), Treaty of Babel (metadata and IDs only), Quetzal (VM saves for one VM family). SCXML is a W3C statechart standard with some research use for game dialogue. Recent efforts (Narrative Context Protocol, 2025) target AI or structure-level portability, not executable narrative logic.

### Cited Findings
- Twee 3 is an interchange format among Twine compilers (Tweego, Extwee, etc.). The Twine 2 HTML spec defines the canonical story-data container. — [twine-specs](https://github.com/iftechfoundation/twine-specs/blob/master/twee-3-specification.md)
- Treaty of Babel defines IFIDs and the iFiction XML format, "specifically designed for metadata interchange among sites like IFDB and the IF Archive, tools such as an Inform or TADS IDE, client programs" **[secondary: search excerpt]** — [Treaty of Babel](https://babel.ifarchive.org/babel_rev9.html)
- Quetzal: "A standard core is defined, and customised information can be stored by specific interpreters in such a way that it can be easily read by others." — [Quetzal 1.4](https://www.ifarchive.org/if-archive/infocom/interpreters/specification/savefile_14.txt)
- W3C selected Harel statecharts as SCXML (Recommendation 2015) as a basis for dialog-system standards. The DEAL project implemented dialogue management in SCXML for "believable game characters". An XPath data model lets SCXML store and manipulate XML data **[secondary: search excerpts of papers]** — [DEAL paper](https://www.researchgate.net/publication/228621365_DEAL_-_Dialogue_management_in_SCXML_for_believable_game_characters); [Statecharts and SCXML for Dialogue Management](https://link.springer.com/chapter/10.1007/978-3-642-40585-3_5); [W3C XPath Data Model for SCXML](https://www.w3.org/TR/scxml-xpath-dm/)
- Narrative Context Protocol (Hank Gerba, USC Entertainment Technology Center; arXiv 2503.04844, 2025): an open-source JSON schema based on Dramatica theory that separates "Narrative Structure" (Dynamics, Storypoints, Storybeats) from "Storytelling" (surface dialogue, actions). Its stated aim is "narrative portability across systems as well as intent-based constraints for generative storytelling systems". — [NCP on alphaXiv](https://www.alphaxiv.org/abs/2503.04844)
- PanelWave: an open JSON Schema (CC BY 4.0) for interactive graphic novels (panel graphs, variables, localization) **[unverified: search result only]** — [panelwave/schema](https://github.com/panelwave/schema)

### Inferences
- Narrata's "abstract narrative logic core" thesis is consistent with NCP's separation of structure from storytelling, and with SCXML's statechart semantics. Exporting statecharts as SCXML could give Narrata an off-the-shelf interchange route for the statechart subsystem (*inference*).
- The lack of a universal format suggests interoperability is best done through **importers/exporters to the de facto formats** (ink JSON, Yarn `.yarnc`/source, Twee 3, articy JSON). These are well specified enough to target.

### Gaps
- No evidence found of 2023–2026 industry-backed universal interactive-narrative interchange standards. Names like "StoryML", "Open Story Format" and "Interactive Fiction Data Format" returned no authoritative results.
- Dialogue System for Unity is widely described as importing from Chat Mapper, articy, Twine, ink, Yarn and CSV, which would make it a de facto conversion hub. No primary Pixel Crushers page confirming that list was retrieved in this session.

## Q8. What do developers and postmortems say about writing-first vs data-first, salience/storylets, and tooling at scale?

### Takeaway
Practitioners agree on two things: **writers must be able to add content without programmers** (Valve, inkle), and **additive, condition-gated content (rules, storylets, salience) scales and updates better than hand-wired branching** (Valve, Emily Short, Yarn 3, Hades). inkle's experience shows inline script authoring enables late rewrites. Visual and database tools are valued but have hit scale walls (Disco Elysium) and complexity costs (CDPR's visual scripting retrospective).

### Cited Findings
- Valve's Ruskin argues against handing writers a spreadsheet to fill per programmer-defined case ("you're basically reducing your writers to filling out a" form). Writers should add rules and facts themselves: "writers can add additional special cases without needing to change any code". "Programmers shouldn't force a workflow on writers... Ask your writers what they want." — [Ruskin GDC 2012 slides](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Ruskin on updates and modding: "this makes modding and user-generated-content easier, because it's all additive. People can always add rules to the system without breaking old ones... modders can add in new special cases for state that exists in the base product... without needing to change the base product." Scoring: "The scoring function that worked best for us was the simplest one imaginable – the number of criteria in a rule." Rules can write facts back as memory, and follow-up lines are queried at callback time, so conversations "self-terminate" when criteria stop holding. He cites Inform's rulebooks cascading from specific to general as prior art. — [Ruskin slides](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Yarn Spinner 3 adopts the same model: node groups (same-name nodes with `when:` headers), line groups (`=>`), and saliency strategies. The default "best" strategy picks the most specific candidate, a direct analogue of Valve's criteria count. — [Yarn Spinner 3.0: What To Expect](https://yarnspinner.dev/blog/yarn-spinner-30-what-to-expect/); [Storylets and Saliency primer](https://docs.yarnspinner.dev/write-yarn-scripts/advanced-scripting/storylets-and-saliency-a-primer)
- Emily Short: storylets are "simple, atomic, robust, and recombinable" and suit "a game that's meant to last for years, to include DLC". Time-cave structures negate their value. Salience-based narrative lets you "build a rudimentary set of content with sensible, broad defaults, and then gradually add new, more salient content". For testing: "run a few thousand randomized playthroughs and use some visualization tools to see whether there were sequences that never got hit". — [Storylets: You Want Them](https://emshort.blog/2019/11/29/storylets-you-want-them/); [Beyond Branching](https://emshort.blog/2016/04/12/beyond-branching-quality-based-and-salience-based-narrative-structures/)
- Failbetter/StoryNexus: qualities are numeric variables representing everything (money, stats, plot progress, items). Storylet cards sit in decks and appear or disappear by quality requirements, location or setting **[secondary: IFWiki]** — [IFWiki: StoryNexus](https://www.ifwiki.org/StoryNexus). Alexis Kennedy later proposed "resource narrative" as an alternative name **[secondary: search excerpt]** — [Wikipedia: Fallen London](https://en.wikipedia.org/wiki/Fallen_London)
- Hades (Kasavin): he wrote as many contexts as possible in which a character could speak and loaded them all so the game holds "the right one for the right situation" **[secondary: search summary of GDC 2021 coverage]** — [GDC 2021 article](https://gdconf.com/article/dive-into-the-dialogue-of-hades-at-gdc-2021/). Kasavin pointed fans to a third-party breakdown of the conversation system ([Kasavin on X](https://x.com/kasavin/status/1329487797607043073)). Requirements live in Lua data (`RequiredTextLines`, in files like `NPCData.lua`/`TextLineSets.lua`) **[community]** — [Hades Wiki talk page](https://hades.fandom.com/wiki/Talk:Epilogue_Guide)
- inkle (Heaven's Vault): finding an authoring pattern "was a really long and difficult, iterative process". The first implementation was "too fiddly" and "very fragile". The final architecture let Ingold rewrite "every single line" of a scene 10 weeks before release without coordinating with environment, character or animation teams. ### Inferences
- Valve rules, Yarn 3 saliency, Hades requirements, Failbetter qualities and Heaven's Vault knowledge-driven conversation all converge on **fact base + condition-gated content units + selection policy**. That is the best-documented architecture for dynamically updated and very long narratives, because new content is added rather than wired in. Narrata's composable narrative node packages plus statecharts should expose this as a first-class mode alongside flow/branching.
- Writing-first (ink) and data-first (articy) camps disagree on authoring UX, not on runtime architecture. Both end up as a compiled graph plus host-interpreted cues. A logic-only core can serve both if it has good text-format and DB-format front-ends, as Valve did with Notepad, Excel and a visual tool feeding one rule format.

## Q9. Net: does industry evidence support Narrata's thesis (abstract logic core, pluggable storage, ultra-long and dynamic narratives, text/media as separate products)?

### Takeaway
**Strong support** for: a host-agnostic logic core (ink and Yarn are middleware by design), ID-referenced text and media, pluggable state/save storage, and additive condition-gated content for long-lived, updateable narratives. **Weak or no precedent** for: pluggable *content* backends queried at runtime (graph DB/Postgres), and save compatibility across content updates. Every surveyed system is fragile there unless authors use explicit stable names. Narrata would be breaking new ground on both and should design deliberately (stable IDs, content revisions, migrations).

### Cited Findings
- Middleware core: ink "isn't designed as an end-to-end narrative game engine... it can slot into your own game and UI with ease" — [ink README](https://github.com/inkle/ink). Yarn has runtimes for Unity, Godot, Unreal (beta) and a JS/NPM runtime — [Yarn 3 blog](https://yarnspinner.dev/blog/yarn-spinner-30-what-to-expect/).
- Text/media separation by ID: Yarn `RunLine` by line ID with a string table per language — [proto](https://github.com/YarnSpinnerTool/YarnSpinner/blob/main/YarnSpinner/yarn_spinner.proto); [v1 docs](https://v1.yarnspinner.dev/docs/unity/components/yarn-programs/). A Valve response is a vox file or animation — [Ruskin](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf).
- Pluggable state storage: Yarn `VariableStorageBehaviour` — [Yarn docs](https://docs.yarnspinner.dev/3.1/components/variable-storage/variable-storage). Pixel Crushers `DataSerializer`/`SavedGameDataStorer` — [PC Save System](https://www.pixelcrushers.com/dialogue_system/manual2x/html/save_system.html).
- Against relational content storage as a native runtime representation: Ruskin's "This is not a relational database" — [Ruskin](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf). Yarn recommends editor-time compilation — [Yarn FAQ](https://docs.yarnspinner.dev/faq).
- Content-update fragility: ink "will never be possible to make this perfect" — [ink releases](https://github.com/inkle/ink/releases). Ren'Py "statements... added to the game won't run" — [Ren'Py docs](https://www.renpy.org/doc/html/save_load_rollback.html). Skyrim mod data baked into saves **[community]** — [AFK Mods](https://www.afkmods.com/index.php?%2Ftopic%2F3676-skyrim-information-baked-into-saves%2F=). Arcweave schema change requires save re-testing — [Arcweave](https://blog.arcweave.com/scoped-variables-in-arcweave-migration-guide).
- Scale via partitioning and streaming: Valve region databases streamed with level data — [Ruskin](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf). articy multi-user partitions and incremental export — [articy 4.0](https://www.articy.com/help/adx/Changes_4_0.html).
- Additive updates: Valve "it's all additive" — [Ruskin](https://steamcdn-a.akamaihd.net/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf). Storylets suit games "meant to last for years, to include DLC" — [Emily Short](https://emshort.blog/2019/11/29/storylets-you-want-them/).

### Inferences
- Recommended layering, consistent with all evidence above: **Authoring sources/DB (pluggable: files, Postgres, graph DB, articy/Arcweave importers)** → **deterministic compiler to an immutable, versioned, content-addressed program with stable node/line IDs** → **runtime VM (Wasm/FFI)** → **state store (pluggable: SQLite/JSON/Postgres) keyed by stable IDs, with save-schema version + content-revision ID + migration hooks** → **text/media products resolved by ID per locale** (string tables, voice, images).
- Narrata's time-travel save store plus determinism is a genuine differentiator. No surveyed engine documents deterministic replay across content revisions. ink stores `storySeed` and `previousRandom` for RNG determinism ([StoryState.cs](https://github.com/inkle/ink/blob/master/ink-engine-runtime/StoryState.cs)), which is the closest prior art.
- To support "dynamically updated narratives" credibly, Narrata needs a documented policy for saves positioned inside changed or deleted content: fall back to the nearest stable anchor (as Ren'Py does), run migrations, and default new variables (as ink and Yarn do). Without one, it inherits the fragility seen across the industry.

### Gaps
- No quantitative evidence was found comparing runtime performance of DB-backed vs compiled-artifact narrative content.
- No live-service narrative game (e.g. Fallen London's years of weekly updates) documented its save/content-versioning approach in sources retrieved here.
